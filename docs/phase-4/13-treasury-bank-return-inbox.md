# 隔离银行回盘、逐行复核与异常冻结

## 三层责任边界

1. 银行连接器领取银行回盘，但不把银行凭据、Token 或原始文件交给 ERP。
2. 独立 Return Inbox 对原始文件执行验签、恶意文件扫描、压缩与大小限制、格式规范化和 WORM 留档，只向 ERP 返回最多 5000 行、4 MiB 的严格 JSON 清单及证据引用。
3. ERP 使用已提交批次中的 Treasury 密文支付指令逐行复核指令 ID 和金额，只保存汇总、证据引用以及 AES-256-GCM 加密的规范化行清单；Mongo、事件、响应、审计、日志和 MCP 均不保存原始文件或明文员工支付行。

Return Inbox 与 ERP、WORM、银行提交网关必须使用不同 HTTPS Origin 和独立凭据。配置缺项、凭据复用、非 443 端口、URL 凭据、查询参数或重定向全部失败关闭。

## 领取与绑定契约

- `POST /treasury/disbursements/:id/returns` 只允许拥有 `erp:treasury:return:ingest` 的受信任 `service` 或 `system_job` 调用；普通用户与 MCP 均不可调用。
- ERP 仅向 Inbox 发送可信租户、批次 ID 和银行提交 ID。确定性幂等键绑定三者，不发送账户、员工、金额或文件内容。
- Inbox 清单必须严格绑定同一租户、ULID 批次和银行提交回执；回盘 ID 为 ULID，接收时间不得超前服务器时间五分钟。
- 当前状态机只接收一份终态回盘，因此序号必须为 1；乱序或增量清单失败关闭且不推进、不冻结批次。未来支持多阶段回盘时必须先扩展显式序列状态机，禁止仅放宽校验。
- 清单必须关联回盘 SHA-256、WORM 对象及证据、签名证据、恶意文件扫描证据。响应出现额外字段、原始正文、错批次、错提交、非法 JSON 或超限时拒绝处理。

## ERP 逐行复核与冻结

- ERP 只从状态为 `submitted` 的批次及其 Treasury 密文支付指令构建期望集合；行数缺失或密文 AAD/业务绑定不一致时失败关闭。
- 每一回盘行必须命中支付指令且金额完全相同。重复行、未知行和逐行金额错位分别独立计数，不进入成功或失败金额。
- 完整成功且签名、扫描、行数、金额全部守恒时，批次只进入 `reconciling`，对应支付指令进入 `succeeded`。
- 恶意文件、签名失败、未知行、重复行、逐行金额错位、总行数不守恒、总金额不守恒或任一失败行均冻结整个批次和所有待回盘指令。冻结原因按文件安全、身份真实性、行真实性、守恒性和部分失败的优先级确定。
- 冻结不代表自动重试或自动解冻。后续只能由受控人工调查形成证据，再创建仅含失败行的新子批次；不得修改、覆盖或重传原批次。

## 数据、事件与审计

- 规范化行清单使用 `resourceType=bank_return`、回盘 ID、序号和可信租户作为 AES-GCM AAD；它为后续失败子批次提供可验证输入，但数据库没有 `lines` 明文字段。
- 回盘记录以可信租户为所有唯一索引首字段，并按租户+回盘摘要、租户+批次+序号防重。幂等重放只允许在批次仍处于本次产生的 `reconciling` 或 `frozen` 状态时返回原汇总。
- `treasury.bank_return.applied.v1` 事件执行精确字段白名单，只发布汇总、冻结原因、摘要和证据 ID，不发布支付指令、银行行引用、员工或账户数据。
- R3 审计只记录聚合摘要。原始回盘、密文解密、冻结解除、失败子批次和银行重发不注册 MCP Tool。

## 失败行恢复子批次

- 只有 `PARTIAL_SUCCESS` 且签名、恶意文件扫描、未知行、重复行和逐行金额全部干净的冻结批次，才允许调用 `POST /treasury/disbursements/:id/recovery`。其他冻结原因必须人工调查，不得自动产生付款。
- 恢复批准人必须是已验证用户，拥有 `erp:treasury:recovery:create`，以绑定父批次 ID 的近期 WebAuthn 用户验证批准，并独立于原工资锁定人、代发制备人和导出批准人。
- 客户端只能提交父批次预期版本和强认证证据，不能选择员工、金额、银行账户或执行日期。失败集合与金额来自加密终态回盘；收款账户来自员工当前已审批活动账户；付款账户沿用已成功执行过部分行的父批次密文快照；执行日期由服务端确定。
- 服务逐行重算成功和失败两侧的数量与金额，并复核父批次、回盘记录、加密清单和全部冻结指令。任何缺失、重复、金额错位、AAD 绑定错误或汇总不守恒都失败关闭。
- 父批次及原支付指令永久保持 `frozen`，不做原地解冻、覆盖或重传。恢复创建 `purpose=recovery` 的新子批次，只复制明确失败金额，并重新使用新指令 ID 经历 WORM、WebAuthn 导出批准和银行提交全控制链。
- 每个直接冻结源最多创建一个恢复子批次，由独立追加迁移建立 `tenantId + recoverySourceBatchId` 唯一索引；后续再次失败必须以新的失败子批次为父级形成可追踪链。
- `treasury.disbursement.recovery_requested.v1` 只发布父批次、工资引用、回盘摘要、失败汇总、状态与强认证方法；不发布员工、指令、账户、批准人或证据明细。该 R3 能力不注册 MCP Tool。
