# ADR-0009：供应方主档与外部履约边界

- 状态：accepted
- 日期：2026-08-10
- 关联 Issue：无（供应方管理体系前置架构）
- 替代关系：无

## 背景

GaoQ 的业务供应方既包括公司，也包括以剪辑、设计、摄影和编导等能力提供服务的
个人兼职者。现有 `creator-service-part-time` 把创作者账号、技能、报价、接单、
合同、钱包和提现组成一条独立链路；若直接把该模型并入 ERP，会把登录身份、供应
关系、劳动关系、履约和支付混在一起，也会带入缺少租户边界、浮点金额和高敏数据
治理不足等风险。仓库现有文档还大量使用“供应商”指代技术接口厂商，继续复用该词
会形成领域歧义。

## 决策

业务交易相对方统一称为“供应方”，软件和接口提供者称为“技术厂商”。GaoQ OS
分别建立 Supplier、Sourcing、Engagement 和 Payables 四个领域：Supplier 只拥有
租户内供应关系、准入结论、服务能力和价目项；Sourcing 拥有需求、邀约和选定；
Engagement 拥有履约委托、履约者、交付、验收和争议；Payables 拥有应付事项并经
Treasury 执行支付。自然人或组织作为供应主体，实际履约自然人单独记录；供应关系
不推导登录权限或劳动关系。

首期在 GaoQ OS 原生建设 Supplier 主档和准入能力。未来接入
`creator-service-part-time` 时通过 Integration 防腐层映射其事实和标识，先完成
一次性迁移与双向对账，再决定门户能力的归属；禁止直接共享数据库、复用旧 JWT、
复制浮点钱包余额或让两个系统同时成为供应方主档事实源。

## 后果

- 个人供应方可以同时是供应主体与履约者；组织供应方必须分别记录签约主体和实际履约者。
- 同一自然人即使同时是员工和履约者，也必须保留两种关系并执行利益冲突、用工分类和审批策略，权限不得继承。
- 合同证据由 Integration/eSign 管理，银行账户和支付由 Treasury 管理，Supplier 只保存受控引用和核验摘要。
- 价目项只是参考价格，成交金额冻结在履约委托中；金额跨边界使用整数分字符串，领域计算使用 BigInt。
- 标准 MCP 首期只提供脱敏只读查询；准入批准、合同签署、银行账户、税务正文、支付、争议裁决和数据删除不注册写 Tool。

## 被否决方案

- 直接 subtree 合并兼职平台：会同时引入第二身份体系、第二财务账和不符合当前安全基线的数据模型。
- 用 `User` 加一个供应商角色：无法表达一个组织多个履约者、同一人多重关系、无账号供应方和关系有效期。
- 建一个覆盖主档、接单、合同、钱包和打款的万能 Supplier 模块：接口过宽，交易和财务规则会持续泄漏到供应方主档。
- 把个人兼职者建成员工或特殊劳动关系：混淆采购服务与劳动关系，带来权限、税务、薪酬及合规误判。

## 安全与数据影响

供应方实名、证件、税务、银行和合同数据属于 L3/L4，必须目的限制、字段加密、独立
盲索引、最小投影和访问审计。个人供应方准入前必须由法务/财务确认适用的用工分类、
代扣代缴、发票或完税凭证规则；仓库实现和自动校验不能替代适用法域的法律结论。
