# GaoQ-OS 安全、质量与统一切换规范

## 1. 安全与隐私基线

- 管理体系对齐 ISO/IEC 27001:2022 和 ISO/IEC 27701:2025。
- 应用安全以 OWASP ASVS 5.0 Level 2 为最低门禁；身份、权限、租户、薪酬、合同、密钥和批量导出按 Level 3 验证。
- 满足中国《网络安全法》《数据安全法》《个人信息保护法》和《网络数据安全管理条例》；具体法律结论由公司法务和合规顾问签署。
- 所有功能先完成数据分类、目的限制、最小收集、保存期限和访问角色，再进入开发。

## 2. 身份、权限与密钥

- 人员登录优先使用钉钉/飞书SSO和企业身份；外部主体使用可验证的手机号/邮箱流程。
- Access Token短期有效，Refresh Token轮换并支持会话级吊销；高风险操作需要近期二次认证。
- 浏览器 Refresh Token 只进入 `HttpOnly + SameSite=Strict` Cookie，数据库只保存
  SHA-256 摘要；每次刷新都原子消费旧令牌、创建同 family 下一代并以 CAS 绑定
  前驱/后继，且新 Access Token 必须在该轮换事务提交前完成签名；签名失败必须
  回滚令牌代次。任一旧令牌重放必须吊销整个 family 与服务端会话。
- Access Token 必须校验签名、`typ=at+jwt`、issuer、audience、resource、会话或
  服务凭据活动状态，并强制 `sub = tenant_id:actor_id`；角色、Scope、部门、
  audience 和 resource 集合不得重复，解析后的可信身份投影必须深冻结。
- OAuth Authorization Code + PKCE 的请求与授权码只保存随机值摘要、短时且
  一次性；每次展示、决策和交换都必须按当前客户端注册表重新校验精确回调、
  resource、租户与 Scope。进程重启或配置收紧后，Redis 中的旧请求不得沿用旧授权。
- JWKS 必须同时发布活动签名公钥和轮换窗口内的历史验签公钥；历史集合只接受
  至少 2048 位 RSA 公钥、唯一 `kid` 和 RS256 验签用途，禁止私钥字段、重复公钥
  材料或与活动 `kid` 冲突。旧公钥须保留至最后一枚旧 Token 过期并越过 JWKS
  缓存窗口后才能移除。
- 权限必须在服务端按菜单、操作、字段、数据范围四层执行；默认拒绝。
- 生产密钥、证书、外部凭据和数据密钥只存KMS/Secret Manager；禁止进入代码、Issue、日志、镜像和CI输出。
- break-glass权限默认关闭、双人批准、限时、全程审计并在使用后复盘。

## 3. 安全开发门禁

每个PR必须通过：

- Lint、TypeCheck、单元/集成/契约测试。
- SAST、SCA、Secret Scan和容器镜像扫描。
- 动态查询字段、排序字段、Mongo操作符和表达式DSL白名单测试。
- XSS、CSRF、SSRF、IDOR、文件上传、Webhook重放和跨租户访问测试。
- 高风险模块的安全负责人评审。

发现硬编码密钥、查询注入、XSS、权限绕过、跨租户泄漏或审计缺失时必须阻断合并。

## 4. 测试标准

| 测试层 | 门禁 |
| --- | --- |
| 单元 | 全局覆盖率≥80%；关键模块≥90% |
| 集成 | MongoDB、Redis、BullMQ、对象存储、KMS及所有适配器成功/失败路径 |
| 契约 | OpenAPI、JSON Schema、CloudEvents、MCP和供应商Webhook |
| 端到端 | 招聘到入职、申请到归档、考勤到薪酬、离职到校友 |
| 安全 | ASVS、租户逃逸、权限矩阵、提示注入、敏感数据泄漏 |
| 性能 | P95<500ms、1000并发、1000人薪资<5分钟 |
| 容灾 | RPO≤15分钟、RTO≤4小时，恢复后数据与事件对账 |

全局覆盖率工具必须显式包含全部生产源码，并在主质量链中执行；禁止依赖“只统计
测试已加载文件”的默认行为。关键模块的逐文件 90% 阈值与全源码四维 80% 阈值
必须同时生效，任一失败即阻断。

测试不得依赖生产个人信息。核心财务用例使用经财务确认的黄金数据集，所有舍入、累计预扣、回盘和重算结果精确比对。

## 5. 发布与可观测性

- 环境按开发、测试、预发、生产、灾备隔离，生产发布只允许CI/CD使用短期身份执行。
- 数据库迁移必须向前兼容、可重复、可观测；破坏性变更采用扩展-迁移-收缩并分版本完成。
- 每次发布提供变更说明、风险、监控、回滚条件、回滚步骤和负责人。
- 告警至少覆盖错误率、延迟、队列积压、外部连接失败、租户拒绝、高风险操作、审计写入失败和备份失败。
- 审计写入失败时，高风险业务采用失败关闭策略。
- Phase 1 审计事件必须持久化为每租户独立的 HMAC 前向链，事件与链头原子提交且不得设置 TTL；完整不可抵赖性仍须通过不同权限域的 WORM 平台周期锚定链头。

## 6. 统一大切换

### 6.1 前置验证

- 旧系统在正式切换前继续作为生产事实源；ERP使用脱敏或受控副本做影子验证。
- 审批至少进行4周影子流程比对，薪酬至少完成2个完整薪资周期影子计算。
- 至少执行3次全量迁移演练，每次生成记录数、关联数、金额、附件、校验和、差异和耗时报告。
- 完成一次生产级回滚演练并在4小时内恢复旧系统服务和一致数据。

### 6.2 Go/No-Go

只有同时满足以下条件才允许上线：

- Sev1/Sev2缺陷为零，安全高危/严重漏洞为零。
- 迁移记录与关联100%对账，未解释金额差异为零。
- 租户、角色、字段、数据范围权限矩阵100%通过。
- 钉钉、飞书、OP、e签宝、银行/税务文件、消息和MCP契约测试通过。
- 备份、恢复、回滚、监控、值班和业务连续性方案均完成演练。
- 项目发起人、产品、架构、安全、数据、HR、财务、法务、QA和SRE共同签署。

### 6.3 切换窗口

统一在周末8小时冻结窗口执行：冻结旧系统写入、导出最终增量、迁移、全量校验、切换身份与外部连接、业务抽样、开放ERP与MCP。任一强制门禁失败立即回滚，禁止在生产中临时修改关键数据后继续上线。

上线后4周进入Hypercare：每日核对组织、审批、签署、薪酬、队列、外部回调和MCP审计；旧系统只读保留至法务、财务和数据负责人批准归档。

## 7. 事故响应

Sev1包括跨租户泄漏、薪酬错误批量发放、权限全面绕过、签署证据损坏和核心服务不可用。Sev1必须立即阻断相关入口、保护证据、启动应急负责人和法务/安全通知流程；恢复后5个工作日内提交无责复盘、根因、修复和防复发门禁。
