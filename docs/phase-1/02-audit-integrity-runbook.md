# Phase 1 持久审计与完整性验证手册

## 1. 交付边界

- `AuditService` 的唯一生产出口是 MongoDB 持久审计链，禁止降级为普通应用日志。
- 每租户独立维护连续序号和前向哈希；事件与链头在同一 MongoDB 事务提交，多实例并发冲突最多重试三次。
- 每条事件使用 HMAC-SHA-256，覆盖租户、主体、动作、资源、风险级别、结果、时间、trace、规范元数据、序号和前一条哈希。
- 审计元数据只保存排序后的受控 JSON 字符串；动态对象、敏感键、非有限数字、超长值和 20 个以上字段均失败关闭。
- 签名与验签入口必须重新校验完整链载荷：只接受固定字段、规范排序后的 JSON
  元数据、正整数序号、受控标识和规范 32 字节 Base64URL 前向哈希；额外字段、
  非规范 Base64URL、乱序 JSON 或绕过元数据敏感键检查全部失败关闭。
- 审计集合没有 TTL。任何保留、归档或删除必须由法务、数据负责人和安全负责人共同批准，不能由应用隐式执行。

HMAC 链能够检测数据库内事件的删除、插入、改序和字段篡改，但数据库管理员仍可能整体重写数据与链头。系统已交付 Ed25519 签名、幂等外部写入与回执持久化适配器；只有生产环境从独立权限域 WORM 平台取得并抽样回读真实回执后，才可宣称该环境具备完整不可抵赖性。

## 2. 密钥环

运行时由 Secret Manager 注入 `AUDIT_INTEGRITY_KEYS`：

```json
{
  "activeKeyId": "audit-2026-q3",
  "keys": [
    {
      "keyId": "audit-2026-q3",
      "keyBase64url": "32字节随机密钥的base64url编码",
      "status": "active"
    }
  ]
}
```

- 只允许一枚 `active`，最多八枚密钥；旧密钥改为 `verify_only`。
- 旧密钥必须保留到对应事件完成 WORM 锚定和法定保留期验证，禁止在链验证前移除。
- 仓库、镜像、Issue、PR、CI 输出和迁移记录中不得出现密钥值。
- 生产环境缺少密钥环时拒绝启动；运行期间密钥不可用或无效时审计写入失败，高风险业务响应失败关闭。

## 3. 验证与告警

- `AuditChainVerificationService.verifyTenant` 按 1000 条分批验证序号、前向哈希、每条 HMAC 与链头。
- 每日对全部活跃租户执行完整性验证；失败码只进入安全告警，不输出事件内容或原始元数据。
- `AUDIT_CHAIN_SEQUENCE_INVALID`、`AUDIT_CHAIN_HASH_INVALID`、`AUDIT_CHAIN_HEAD_INVALID` 均按 Sev1 安全事件处理：冻结审计依赖的 R2/R3 操作、保护数据库与平台日志证据并启动事件响应。
- 监控至少覆盖写入失败率、事务重试次数、验证耗时、最后成功锚定时间、链头序号停滞和 WORM 导出失败。

## 4. 验收

- Replica Set 中并发追加同租户事件，最终序号连续、无重复且链头一致。
- 修改任一已持久事件字段后，完整性验证必须失败；恢复原值后再次通过。
- 密钥轮换后新事件使用新 keyId，历史事件继续由 `verify_only` 密钥验证。
- 数据库不可用、事务失败或密钥缺失时，R2/R3 入口不得返回成功。
- Mongo 已确认事务提交后若仅 `endSession` 清理失败，只记录稳定告警，禁止把已
  落盘审计暴露为失败并由调用方生成另一 eventId；事务未提交时的清理故障仍失败关闭。
- 使用真实独立 WORM 平台验证重复幂等提交、保留期锁定、对象回读和 Ed25519 验签；Mock 回执不得作为生产验收证据。
- 索引迁移 `phase-1-indexes-v3` 必须验证 19 个集合、63 个声明索引。
